# TRACKER V173 — стабильный BLE + без циклической перезагрузки Analytics

Дата: 2026-08-20

## Что было найдено

1. **Автоматический GPS recovery сам перезапускал Analytics.**
   Каждый статус `waiting / reconnect / recording` запускал таймер, затем увеличивал `dataRevision` и вызывал общий `_loadServerData()`. При pending recovery это повторялось циклически, поэтому выбранная сессия выглядела как `данные → загрузка → данные → загрузка`.

2. **Архивная выбранная сессия всё ещё зависела от текущего Live.**
   В ключ `_bundleRequestKey()` входили `widget.liveRunning` и `localPoints.length`. Если параллельно шёл новый Live, каждая новая локальная GPS-точка могла инвалидировать Future уже сохранённого матча.

3. **При `dataRevision` удалялся `_lastBundle`.**
   Даже корректное одноразовое обновление после recovery очищало уже показанный экран и возвращало полный loader вместо тихого обновления поверх текущих данных.

4. **Фоновые BLE логи/keep-alive слишком часто перестраивали весь workspace.**
   Командный pool отправляет служебные ответы и логи даже вне Live. Они вызывали `setState()` верхнего экрана, хотя пользователь мог смотреть архивную аналитику.

5. **Post-Stop recovery был слишком агрессивным для Android GATT.**
   Один background-pass мог делать до 4 `connectGatt` попыток подряд для каждого GPS. На нескольких датчиках это усиливало GATT 133 и создавало серию `Отключение...`.

## Что изменено

- Recovery обновляет Analytics **только после реального изменения данных**: `GPS recovery готов` / `GPS восстановлен`.
- Waiting/reconnect статусы больше не увеличивают `dataRevision` и не запускают общий server reload.
- Несколько завершившихся GPS объединяются в один refresh с debounce 2.2 сек.
- Background `_loadServerData` получил `silent` режим и защиту от параллельных запросов.
- После Stop и после служебных привязок server refresh выполняется без мигания глобального loader.
- Выбранная сохранённая сессия больше не зависит от текущего `liveRunning` и `localPoints.length`.
- `_lastBundle` сохраняется при recovery-refresh: старые данные остаются видимыми, пока новые тихо загружаются.
- BLE data/log/state не перестраивают архивный экран Analytics, когда эти данные на нём не нужны.
- Post-Stop auto recovery выполняет **1 прямую BLE попытку на pass**, а не 4 подряд.
- Интервал background recovery увеличен с 15 до 30 секунд.
- Idle reconnect для незакрытого командного канала ограничен минимум 30 сек между попытками.
- Намеренное закрытие старого GATT перед reconnect теперь логируется как `BLE reconnect cleanup`, а не как безымянная ошибка `Отключение...`.
- Реальный `Android GATT 133` по-прежнему остаётся ошибкой в Remote Debug — он не маскируется.

## Ожидаемое поведение

### Analytics
- Открыть сохранённую сессию и оставить экран на 2–3 минуты во время pending recovery.
- Экран не должен снова уходить в полный `Загружаем данные выбранной сессии…`.
- Когда один/несколько GPS реально восстановят точки, Analytics обновится один раз; уже показанный контент останется на экране, максимум появится тонкая полоса обновления.
- Если одновременно идёт новый Live, его GPS-точки не должны перезапускать загрузку старого выбранного матча.

### BLE / Recovery
- При GPS вне зоны возможны `GATT 133`, но не должно быть четырёх быстрых reconnect-попыток подряд для одного background recovery.
- Намеренный reset GATT отображается как cleanup, а не как отдельная критическая ошибка.
- Auto recovery остаётся автоматическим: после возвращения GPS в зону файл будет найден и дополнит ту же final session.
- Новый Team Live по-прежнему имеет приоритет над чтением старых ATP файлов.
