# SPORTOTEKA Tracker V165 — полный матч ATP + новый Live без ожидания recovery

## Что объединено

V165 включает V159/V164 fixes и добавляет главное рабочее правило:

- после `Stop` полный GPS-файл ATP автоматически восстанавливает уже созданную финальную сессию;
- если восстановление старого матча ещё идёт, **новую Team Live-сессию можно запускать**;
- новый Live всегда имеет приоритет над чтением архива ATP;
- recovery старого матча не удаляется и автоматически продолжается после следующего `Stop`.

Новая тренировка не создаёт дубль старой. Каждый recovery job остаётся привязан к своему
`final_session_id`, игроку, UUID/MAC и временному окну матча.

## Нормальный сценарий

1. Матч №1 идёт в Team Live.
2. Тренер нажимает `Stop`.
3. Сервер создаёт final session и recovery job на полное окно матча.
4. Приложение сразу ищет соответствующий ATP file.
5. Если file уже `finished`, начинается автоматическая выгрузка.
6. Если file ещё `recording`, GPS далеко или Android дал GATT 133 — job остаётся waiting/pending.
7. Recovery повторяется автоматически каждые 15 секунд.
8. Тренер может нажать `Start` и начать Матч №2, не ожидая окончания Матча №1.
9. Если в этот момент ATP отдавал старый файл или record-list, V165 немедленно ставит BLE recovery на паузу.
10. Тот же ATP переподключается и используется для текущего Live.
11. Во время Матча №2 старый BLE-файл не читается — Live GPS имеет абсолютный приоритет.
12. После `Stop` Матча №2 recovery автоматически продолжает очередь Матча №1 и затем Матча №2.

## Что именно ставится на паузу при новом Start

Раньше прерывался только уже начатый `downloadFinishedRecord()`. Это оставляло узкое окно:
Start мог прийти, пока recovery ждал `requestRecordListFor()` до 12 секунд, и старый BLE-запрос
продолжал держать GATT/общую очередь.

V165 ставит на паузу **весь BLE recovery**:

- активный download 44/45;
- активный запрос списка ATP-файлов;
- остаточный selected record;
- GATT старого recovery-канала.

Технический interrupted-буфер никогда не отправляется на сервер. Recovery job остаётся waiting,
а после Stop нужный finished-файл читается заново целиком.

Это специально сделано для защиты от Android `GATT 133` и от частичного восстановления маршрута.

## Полное автоматическое восстановление матча

Для каждого GPS после Stop:

1. создаётся/подхватывается server recovery job;
2. сохраняется точный игрок + UUID/MAC + `liveStartedMs/liveStoppedMs` + `final_session_id`;
3. приложение восстанавливает BLE точного ATP, даже если GATT 133 ранее удалил соединение;
4. запрашивает список файлов;
5. выбирает файл по пересечению со временем конкретного матча, а не просто «последний finished»;
6. при необходимости учитывает безопасный clock shift ATP;
7. ждёт `finished`;
8. скачивает запись;
9. оставляет только точки окна нужного матча;
10. отправляет их batch-ами в staging recovery job;
11. `finalizeOfflineRecovery()` дополняет существующую final session и пересчитывает её;
12. UI сбрасывает cache и перечитывает карту/аналитику.

Уже принятые Live-точки не должны удваиваться — серверный recovery используется как дополнение
существующей сессии.

## Очередь нескольких матчей

Допустимый сценарий:

- Матч №1 — recovery waiting;
- Матч №2 — Live идёт;
- Матч №1 BLE recovery paused;
- Stop Матча №2;
- recovery снова активируется;
- незавершённые jobs обоих матчей обрабатываются последовательно.

Ни `Start`, ни создание следующей final session не должны удалять старые pending/waiting jobs.

## Единственное исключение для Start

Если предыдущая тренировка была полностью local-only и сервер ещё **вообще не создал** её
`final_session_id/recovery job`, V165 сначала пытается зарегистрировать её на сервере.

Пока это не получилось, новый Start блокируется. Это намеренно: иначе пришлось бы очищать `_runtime`
предыдущего локального матча до появления безопасной серверной ссылки и можно было бы потерять его
контекст.

Обычный pending/waiting recovery уже созданной final session **новый Start не блокирует**.

## Recovery после ухода с экрана

После Stop coordinator удерживает shared BLE pool background lease, пока сервер возвращает
pending/waiting jobs. Закрытие workspace не должно убивать recovery. При повторном открытии Tracker
сохранённые GPS-привязки подхватываются и старые jobs проверяются снова.

## Карта после восстановления

После успешного `finalizeOfflineRecovery()` увеличивается revision данных. Аналитический bundle и
календарный cache сбрасываются, серверная сессия перечитывается. Поэтому карта должна показать
восстановленный полный маршрут без ручного закрытия/открытия раздела.

## Ручная страховка

Кнопка `Восстановить GPS` остаётся в `Устройствах` и `Истории`. Она показывает:

- игрока и ATP;
- BLE online/ожидание;
- recovery job;
- final session;
- file id;
- `recording/finished`;
- размер;
- clock shift;
- последнюю причину ожидания.

`Восстановить сейчас` использует тот же безопасный путь и не создаёт отдельную тренировку.
Во время текущего Live ручной BLE recovery не запускается.

## Что искать в Remote Debug

Нормальные маркеры:

- `team_offline_recovery_job` — создан job полного матча;
- `POST-STOP AUTO RECOVERY` — попытка вернуть BLE после Stop;
- `OFFLINE DOWNLOAD START` — началось чтение finished-файла;
- `OFFLINE RECOVERY PAUSE · приоритет новому Team Live` — тренер запустил новый Live во время recovery;
- `team_offline_recovery_wait` — ATP пока недоступен/не finished;
- `team_offline_recovery_clock_shift` — применён сдвиг часов;
- `OFFLINE DOWNLOAD DONE` — файл прочитан;
- `team_offline_recovery_done` — final session дополнена.

## Как проверить V165

### Тест A — обычный полный матч

1. Запустить Team Live на 5–10 минут.
2. Stop.
3. ATP оставить рядом.
4. Не нажимать ручную загрузку.
5. Дождаться `team_offline_recovery_done`.
6. Проверить полный маршрут и дистанцию в той же финальной сессии.

### Тест B — новый матч во время recovery

1. Матч №1 → Stop.
2. Пока виден waiting/download recovery, сразу нажать Start Матча №2.
3. Start должен пройти без ожидания окончания старого файла.
4. В Remote Debug должна появиться `OFFLINE RECOVERY PAUSE`.
5. Матч №2 должен получать Live GPS как обычно.
6. Stop Матча №2.
7. Recovery должен продолжиться автоматически.
8. Проверить, что обе final session имеют свои маршруты и нет дублей тренировок.

### Тест C — GATT 133

1. После Stop унести один ATP до потери BLE.
2. Убедиться, что job остаётся waiting.
3. Вернуть ATP к планшету.
4. V165 должен сам переподключить сохранённый UUID/MAC и продолжить recovery.

## Установка

Заменить папку:

`lib/presentation/tracker/`

содержимым `tracker/` из архива V165.

Серверная часть `tracker_offline_recovery.php` должна оставаться актуальной из уже установленной
ветки V154/V155/V159. Новых SQL-миграций для этого клиентского патча нет.

## Проверка исходников

В среде подготовки нет Flutter/Dart SDK, поэтому полноценные `flutter analyze` и build здесь не
выполнялись. Diff проверен на whitespace errors, а изменённые участки просмотрены статически.
